# Выбор api-gateway
Исходя из описанных критериев я бы выбрал kong для большинства случаев, кроме реализации api gateway в большой компании, где бы рассмотрел чистый nginx засчет более высокой производительности и максимальной гибкости засчет разработки собственных плагинов.

### Основные критерии

| Критерий | Kong | Nginx | AWS API Gateway |
|:---|:---|:---|:---|
| **Маршрутизация запросов** | ✅ **Да (гибкая)**<br/>Через Services и Routes с управлением через REST API. | ✅ **Да (базовая)**<br/>Ручная настройка в `nginx.conf` через `location` и `upstream`. | ✅ **Да (интегрированная)**<br/>Настройка через консоль AWS или Swagger/OpenAPI. |
| **Проверка аутентификации** | ✅ **Да (мощная)**<br/>Готовые плагины: JWT, OAuth 2.0, API Keys, LDAP. | ✅ **Да (ручная)**<br/>Через модуль `auth_request` с отправкой подзапроса к внешнему сервису. | ✅ **Да (встроенная)**<br/>AWS IAM, Lambda Authorizer, Amazon Cognito, API Keys. |
| **Терминация HTTPS** | ✅ **Да**<br/>Поддерживается на уровне балансировщика. | ✅ **Да (родная)**<br/>Директивы `ssl_certificate` и `ssl_certificate_key`. Гибкая настройка TLS. | ✅ **Да (управляемая)**<br/>Автоматические сертификаты AWS Certificate Manager (ACM). |

### Дополнительные критерии

| Критерий | Kong | Nginx | AWS API Gateway |
|:---|:---|:---|:---|
| **Тип решения** | Open-source / Cloud | Open-source | Managed service |
| **Поддержка Kubernetes** | ✅ **Да** (Ingress Controller) | ⚠️ Ограниченно (через сторонние контроллеры или ручную настройку) | ✅ **Да** (через AWS Load Balancer Controller) |
| **Поддержка GraphQL** | ✅ **Да** (плагины для кэширования, ограничения скорости) | **✅ Да (базовое проксирование)**<br/>**Nginx передаёт GraphQL-запросы как обычный HTTP-трафик. Понимание схемы, кэширование по запросу и федерация требуют отдельного GraphQL-сервера.** | ✅ **Да** (через интеграцию с AppSync или Lambda) |
| **Поддержка BFF** | ✅ **Да** (можно создавать отдельные экземпляры под каждый клиент) | ✅ **Да** (ручная настройка отдельных серверов/локаций) | ✅ **Да** (создание отдельных API для мобильных, веб, админки) |
| **Агрегация запросов** | ✅ **Да** (через плагины или серверные функции) | ❌ Нет (только проксирование, агрегацию нужно реализовывать отдельно) | ✅ **Да** (через интеграцию с Lambda) |
| **Rate limiting** | ✅ **Да** (готовый плагин, гибкая настройка) | ✅ **Да** (модуль `limit_req`, ручная настройка) | ✅ **Да** (встроенный, через Usage Plans) |
| **Кэширование** | ✅ **Да** (плагин proxy-cache) | ✅ **Да** (через `proxy_cache`) | ✅ **Да** (встроенное кэширование ответов) |
| **Circuit breaker** | ✅ **Да** (плагин) | **⚠️ Ограниченно**<br/>**Через параметры `max_fails` и `fail_timeout` в `upstream` блоке. Полноценного паттерна с состояниями нет, но базовая отказоустойчивость доступна.** | ⚠️ Частично (через интеграцию с AWS X-Ray и настройки таймаутов) |
| **Логирование и мониторинг** | ✅ **Да** (плагины, Prometheus/Grafana) | ⚠️ Базовое (логи в файлы, мониторинг через сторонние инструменты вроде `nginx-module-vts` или `nginx-prometheus-exporter`) | ✅ **Да** (CloudWatch, X-Ray, встроенные метрики) |
| **Интеграция с Mock API** | ✅ **Да** (переключение маршрутов между real и mock) | ✅ **Да** (условное проксирование через `if` или переменные) | ✅ **Да** (mock-интеграции в Swagger) |
| **Версионирование API** | ✅ **Да** (через пути, хосты или заголовки) | ✅ **Да** (ручное через пути `/v1/`, `/v2/`) | ✅ **Да** (встроенное, через stages и canary-развертывания) |

### Общие критерии

| Критерий | Kong | Nginx | AWS API Gateway |
|:---|:---|:---|:---|
| **Производительность** | **Высокая.** Основан на Nginx, минимальные накладные расходы. Подходит для высоконагруженных систем. | **Очень высокая.** Эталон производительности среди веб-серверов и прокси. Минимальное потребление ресурсов. | **Высокая.** Небольшая задержка из-за облачной инфраструктуры, но автоматическое масштабирование компенсирует пиковые нагрузки. |
| **Простота настройки** | **Средняя.** Требует понимания плагинов и администрирования БД (PostgreSQL/Cassandra), но есть GUI и декларативный подход. | **Низкая.** Только ручное редактирование конфигурационных файлов. Высокий порог входа для сложных сценариев. | **Высокая.** Управление через веб-консоль или Infrastructure as Code (CloudFormation, Terraform). Интуитивно понятный интерфейс. |
| **Функциональность** | **Широкая.** Большой выбор встроенных плагинов, возможность кастомных решений на Lua. Полноценный API Gateway "из коробки". | **Базовая.** Основной фокус на проксировании и балансировке. Расширенные функции требуют отдельных сервисов или модулей. | **Очень широкая.** Глубокая интеграция с экосистемой AWS, трансформация запросов/ответов, валидация схем, канареечные развёртывания. |
| **Стоимость** | **Низкая (Open-source) / Средняя (Enterprise).** Бесплатная версия покрывает большинство нужд. Платные функции безопасности и аналитики. | **Минимальная (Open-source).** Nginx OSS бесплатен. Nginx Plus требует платной подписки. | **Средняя / Высокая.** Оплата за каждый вызов API и объём переданных данных. При больших объёмах затраты могут быть значительными. |
| **Масштабируемость** | **Хорошая.** Горизонтальное масштабирование с собственной БД или в Kubernetes. Требует ручной настройки. | **Хорошая.** Легко масштабируется горизонтально за балансировщиком. Не требует внешней БД. | **Автоматическая.** Сервис сам масштабируется под нагрузку без вмешательства администратора. |
| **Экосистема** | **Богатая.** Множество готовых плагинов, интеграции с K8s, Prometheus, OpenTelemetry. Активное сообщество. | **Зрелая.** Огромное сообщество и документация, но большинство расширений — сторонние модули. | **Глубокая интеграция с AWS.** Сервисы Lambda, DynamoDB, S3, Cognito работают бесшовно. За пределами AWS возможности ограничены. |

# Выбор брокера сообщений
Исходя из описанных критериев я бы выбрал Kafka для большинства случаев, кроме случая, когда сообщения для потребителей будут довольно редкими и push модель подошла бы лучше, тогда выбрал бы RabbitMQ

| Возможность | Apache Kafka | RabbitMQ | NATS + JetStream |
| :--- | :--- | :--- | :--- |
| **Кластеризация для надёжности** | ✅ Поддерживается | ✅ Поддерживается | ✅ Поддерживается |
| **Хранение сообщений на диске** | ✅ Всегда на диске | ✅ Поддерживается | ✅ (в JetStream) |
| **Высокая скорость работы** | ✅ Очень высокая | ❌ Средняя | ✅ Очень высокая |
| **Поддержка различных форматов** | ✅ Любые | ✅ Любые | ✅ Любые |
| **Разделение прав доступа** | ✅ (ACL на топики) | ✅ (vhost/пользователи) | ✅ (аккаунты/пользователи) |
| **Простота эксплуатации** | ❌ Сложный | ❌ Средней сложности | ❌ Сложнее базового NATS |
| **Модель работы pull/push** | **Pull** (преимущественно) | **Push** и **Pull** | **Pull** и **Push** |
